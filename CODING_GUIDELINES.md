# Coding Guidelines команды
## 1. Структура репозитория

```text
project/
├── backend/
│   ├── app/                 # Точка входа, модули и общая инфраструктура
│   ├── migrations/          # История изменений схемы базы
│   ├── tests/               # Модульные и интеграционные тесты
│   └── pyproject.toml       # Настройки инструментов Python
├── frontend/
│   ├── src/
│   │   ├── app/             # Маршруты и провайдеры приложения
│   │   ├── features/        # Поиск, рецепты, авторизация, папки
│   │   └── shared/          # Общие UI-компоненты и транспорт API
│   ├── tests/               # Сквозные тесты
│   └── package.json
├── docs/                    # Контракты и архитектурные решения
├── compose.yaml              # Локальный запуск зависимостей
├── .editorconfig
├── .gitignore
└── README.md
```

### Как раскладывать код

| Что добавляем | Куда помещаем |
|---|---|
| Поиск и лента | `backend/app/modules/catalog/` и `frontend/src/features/catalog/`. |
| Редактирование рецепта | `backend/app/modules/recipes/` и `frontend/src/features/recipe-editor/`. |
| Папки и «Избранное» | `backend/app/modules/folders/` и `frontend/src/features/folders/`. |
| Общий клиент HTTP и кнопки | `frontend/src/shared/api/` и `frontend/src/shared/ui/`. |
| Контракт API или архитектурное решение | `docs/`. |


## 2. Форматирование и читаемость

| Правило | Python | TypeScript и React |
|---|---|---|
| Форматирование | Ruff Formatter или Black | Prettier |
| Линтинг | Ruff | ESLint |
| Отступы | 4 пробела | 2 пробела |
| Имена | `snake_case` для функций и переменных, `PascalCase` для классов | `camelCase` для функций и переменных, `PascalCase` для компонентов и типов |

- Имена пишите на английском и используйте термины предметной области. При необходимости указывайте единицы измерения в имени, например `timeout_seconds`.
- Давайте функциям имена по действию и держите каждую функцию в рамках одной ответственности. Необычное условие можно выразить именованной переменной. 
- Если значение имеет смысл для домена, дайте ему имя. Например, `MAX_RECIPES_PER_FOLDER` обозначает бизнес-ограничение.
- Группируйте импорты средствами линтера. Зависимости между функциональными модулями проводите через их явно доступные интерфейсы.

### Комментарии

По умолчанию код читается по именам, типам и структуре. Убирайте комментарии, которые пересказывают следующую строку. Закомментированный старый код удаляйте.

Короткий комментарий уместен, если объясняет **причину**, которую нельзя вывести из кода. Например, зачем нужна блокировка строки перед проверкой лимита, почему используется временный обход ограничения внешнего API или какую гарантию нельзя нарушать при рефакторинге. Для публичной функции используйте docstring или JSDoc, если одного имени и типов недостаточно, чтобы объяснить контракт. Временный `TODO` связывайте с задачей.

## 3. Бэкенд

- Держите HTTP-обработчики короткими. Они принимают валидированные данные, передают выполнение прикладной логике и формируют ответ. Бизнес-правила и границы транзакций находятся в прикладном коде. Запросы к БД удобно группировать отдельно, когда это упрощает чтение или тестирование.
- Валидируйте входные данные на границе API и проверяйте права на сервере. Для доступа к пользовательскому объекту проверяйте принадлежность объекта текущему пользователю.
- Выражайте ограничения данных в PostgreSQL там, где это возможно. Используйте внешние ключи, уникальность и ограничения значений. Проектируйте запись с учётом конкурентных запросов и безопасных повторов.
- Возвращайте стабильные коды ошибок и понятные сообщения. В логах оставляйте сведения, нужные для диагностики, исключая пароли, токены и секреты.
- Проводите изменения схемы через версионируемые миграции. Проверяйте применение на чистой базе и обновление с предыдущей версии. Если в общей среде уже применена миграция, исправляйте схему новой ревизией.

## 4. Фронтенд

- Разделяйте серверные данные, состояние интерфейса и состояние маршрута. Серверные данные загружайте и обновляйте через общий слой запросов. Для открытого меню подойдёт локальное состояние, а параметры поиска удобно хранить в URL, если результатом нужно делиться.
- Типизируйте компоненты и сетевые контракты. Ответ, полученный по сети, считайте внешними данными. Используйте схемы валидации там, где ошибка формы данных может нарушить работу приложения.
- Для запросов показывайте загрузку, пустой результат и ошибку там, где это помогает пользователю. Во время сохранения защищайте форму от случайной повторной отправки. После успешной записи обновляйте затронутые данные в кэше.
- Используйте кнопку для действия и ссылку для перехода. У полей должны быть подписи. Проверяйте управление с клавиатуры, видимый фокус и отображение на узком экране.
- Держите стили компонента рядом с ним. Общие цвета, интервалы и типографику задавайте через единые переменные дизайна.

## 5. Контракты и зависимости

Владельцы API и экрана заранее согласуют метод, путь, поля запроса и ответа, коды ошибок, авторизацию и правила пагинации. Публикуйте контракт в OpenAPI и сверяйте с ним типы клиента и моки. Примеры в документации должны соответствовать контракту. Если изменение несовместимо с текущим клиентом, согласуйте порядок выкладки или переходный период.

Фиксируйте разрешённые версии зависимостей через lock-файл или эквивалентный механизм. Секреты задавайте средствами окружения. В репозитории храните пример настроек с безопасными значениями, а локальные секреты, виртуальные окружения и результаты сборки исключайте из Git.

## 6. Тесты, ревью и CI

| Что меняется | Что проверяем |
|---|---|
| Бизнес-правило | Модульный тест для основного случая и значимых границ. |
| API или работа с БД | Интеграционный тест запроса, записи и ожидаемой ошибки. Для защищённых ресурсов проверяем права доступа. |
| Интерфейс | Взаимодействие пользователя, отображение загрузки и ошибки. |
| Критичный сценарий между слоями | Сквозная проверка через браузер и реальный API. |
| Исправление ошибки | Регрессионный тест, который падает на прежнем поведении. |

На каждый PR CI запускает форматирование в режиме проверки, линтинг, проверку типов, тесты и сборку фронтенда. Для изменений схемы в CI поднимайте тестовую базу и применяйте миграции. Защитите `main` и сливайте изменения после прохождения обязательных проверок и ревью.

## 7. Ветки, коммиты и Pull Request

### Названия веток

Используйте `<тип>/<тема>`, например `feat/folder-recipe-picker`. 

| Тип | Назначение | Пример |
|---|---|---|
| `feat` | Новое поведение | `feat/folder-recipe-picker` |
| `fix` | Исправление ошибки | `fix/folder-pagination` |
| `refactor` | Внутреннее изменение без изменения поведения | `refactor/auth-session` |
| `docs` | Документация | `docs/local-setup` |
| `test` | Тесты | `test/folder-permissions` |
| `chore` | Настройки и обслуживание | `chore/add-ci-checks` |

Держите одну короткоживущую ветку на задачу. Используйте `main` как общую ветку интеграции. При зависимости от другого PR укажите, какой PR должен слиться первым.

### Сообщения коммитов

Используйте `<тип>(<область>): <действие>`. Область можно опустить для изменения всего проекта. Пишите короткую фразу на английском с глагола и без точки.

```text
feat(folders): add recipe picker
fix(auth): clear session after logout
refactor(catalog): extract search query builder
docs: explain local setup
```

Один коммит — одно логическое изменение. Исправление и тест, который его проверяет, могут быть в одном коммите. Перед коммитом просмотрите `git diff --staged`. Если из заголовка и кода трудно понять причину или последствия изменения, добавьте пояснение в тело коммита после пустой строки.

### Порядок работы

1. **Создайте ветку от свежей `main`.** Проверьте `git status --short`. Если есть незавершённые правки, сначала сохраните их в своей ветке. Затем выполните:

   ```bash
   git switch main
   git pull --ff-only
   git switch -c feat/folder-recipe-picker
   ```

2. **Опубликуйте ветку.** Для первого push используйте `git push -u origin HEAD`. Черновой PR можно открыть заранее, чтобы обсудить контракт или показать зависимость от другого PR.
3. **Синхронизируйте ветку при необходимости.** Выполните `git fetch origin`, затем в ветке задачи сделайте `git merge origin/main`. Разрешите конфликты по смыслу и повторите проверки. Для личной ветки допустим `git rebase origin/main`, если другие не используют её коммиты. Для обновления опубликованной ветки после rebase согласуйте переписывание и используйте `git push --force-with-lease`. Историю `main` и общих веток не переписывайте.
4. **Откройте PR в `main`.** Укажите что изменилось, как это проверить и какие миграции, настройки или другие PR нужны. Запросите хотя бы одно ревью коллеги по стеку. При изменении API подключите разработчика второй стороны. Замечания исправляйте в той же ветке.
5. **Слейте после ревью и успешного CI.** Для ветки задачи используйте `Squash and merge`. Заголовок итогового коммита оформите по общему шаблону. После слияния удалите удалённую ветку и обновите локальную `main`.
6. **Отменяйте слитые изменения через новый PR.** Используйте `git revert` или кнопку **Revert**. Если изменение уже затронуло схему или данные базы, отдельно согласуйте, как их восстановить.
